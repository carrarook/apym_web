# APYM G2 Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Enforce per-gym APYM roles and tenant isolation in Gymkhana, while preserving NextAuth and documenting the future APYM identity contract without connecting to .NET.

**Architecture:** `AccountMembership` is the required account access link and account-level `OWNER`/`ADMIN` authority. `STAFF` receives exactly one active per-gym role from `GymStaffAssignment`; all API permissions derive from a server-resolved context, and teacher access additionally requires an active `TrainerClient` for that member and gym. Schema/migration files may be authored for review, but no migration is applied and no database is changed.

**Tech Stack:** Next.js App Router, NextAuth, TypeScript, Prisma 6, PostgreSQL, Jest, Zod.

**Spec:** `docs/superpowers/specs/2026-11-16-apym-g2-phase1-design.md`

## Global Constraints

- Keep NextAuth as the web login; do not mint Supabase JWTs or use service credentials as a teacher identity.
- An active `AccountMembership` is required; no authorization fallback from `User.role` or `User.accountId`.
- `OWNER`/`ADMIN` manage gyms in their own account, not platform-wide routes. `STAFF` requires an active gym assignment.
- `User.isTrainer` remains for compatibility only and never grants business permission.
- `TrainerClient` must match trainer, member, gym, active flag, and effective date range for teacher access.
- Do not implement the prescription editor, data synchronization, APYM JWT issuance, or .NET middleware changes.
- Do not execute migrations, alter a database, use production secrets, or infer staff roles automatically from `isTrainer`.
- Keep unrelated G1 working-tree changes intact.

## Review Focus

- A user with no or inactive account membership but legacy `User.accountId` or NextAuth `ADMIN` is denied. Pin in account-scope and guard tests.
- One user can be `TRAINER` in Gym A and `RECEPTION` in Gym B; switching request gym cannot carry permissions over. Pin in authorization and handler tests.
- `isTrainer=true` with no active gym assignment grants no role; a `TRAINER` assignment without matching `TrainerClient` grants no access to the member. Pin in role and delegation tests.
- `OWNER`/`ADMIN` retain account-wide gym management but do not gain platform-only authority. Pin in guard tests for health/admin handlers.
- Concurrent role changes cannot leave two active assignments for the same user/gym. Pin with the partial unique index and transaction test; do not rely on an application-only check.
